# Broker Trade Import

**Status:** Phase 2, first feature. Fully built and unblocked — migration `0011` was applied to the live project on 2026-09-28 (Steve ran `supabase db push`), so `importBrokerTrades`'s `asset_history` write now succeeds end-to-end.

Scope: import trades from a broker export (starting with Saxo Bank), a user-mapped generic CSV, or manual entry — net them into Equities holdings, and visualize the result on a new "Portfolio Performance" stacked area chart on the dashboard. Follows this app's existing category-metadata-in-jsonb pattern (no new tables) and its existing Edge-Function-free, purely-server-action write pattern (no external API involved — this is all user-uploaded-file parsing, unlike DARI/CoinGecko/Finnhub).

## Add Investments UI
`src/components/add-investments-dialog.tsx` — a modal (matching `AddAssetDialog`'s pattern), mounted on the dashboard next to "Add Asset". A small state machine, not three separate dialogs, since the back half (aggregated-holdings preview → confirm → import-result) is identical regardless of entry point:
- **Select** — three method cards: "Upload via broker", "Upload via file", "Individually add trade".
- **Upload via broker** → a grid of broker cards from the registry (Saxo Bank only today, single-letter avatar fallback — no logo image assets in this app) → a dropzone accepting that broker's declared extensions (`.xlsx`/`.csv` for Saxo).
- **Upload via file** → a `.csv`-only dropzone, then a column-mapping step (Ticker/Buy-Sell/Quantity/Price/Date columns + date format + currency) reusing the exact "never guess an ambiguous mapping" principle as [[CSV-Bank-Uploads|CSV Bank Uploads]]'s bank importer.
- **Individually add trade** → a plain form (ticker, instrument name, buy/sell, date, quantity, price + currency) for one trade.
- All three funnel into a shared **Preview** stage and a shared **Result** stage (per-ticker created/updated/unchanged/error outcome) — one bad ticker doesn't abort the batch.

### Per-Trade Review Table (2026-09-28)
The Preview stage originally showed only an aggregated-by-ticker summary (net quantity, trade count, currency) — never the individual trades. Replaced with a Sharesight-style **per-trade editable table**: one row per parsed trade, with Date/Type/Quantity/Price editable inline via plain `<Input>`/`<Select>` cells, row checkboxes + a bulk "Delete" button, a per-row delete icon, and click-to-sort column headers (`ArrowUp`/`ArrowDown`/`ArrowUpDown` from `lucide-react`).
- **Two new fields**: `exchangeRate` and `brokerage`, added as optional fields on `ParsedTrade` (`lib/parsers/types.ts`) and `EquityTrade` (`lib/equities.ts`). No parser (Saxo, generic CSV, manual) populates them — confirmed Saxo's real "Trades" sheet has no FX-rate or commission column (a "Spread cost" field exists but reads 0 for market orders, and "Conversion Rate" only exists in the separate "Transactions" sheet). `add-investments-dialog.tsx` fills `exchangeRate: 1, brokerage: 0` as UI defaults the moment trades land in its own state, editable per row from there. **Not yet factored into `estimateCostBasisUnitPrice`'s cost-basis math** (`dashboard/actions.ts`) — captured and persisted, but valuation still uses price × quantity only; wiring FX/brokerage into cost basis is a separate decision, not assumed.
- **Instrument (ticker/exchange) stays read-only** in the table, deliberately — it drives which existing Equities asset a trade matches or which new one gets created, so making it freely editable risked silently merging a trade into the wrong asset.
- **Sort implementation note**: sorting never reorders the underlying `trades` state array — a `displayOrder` (an array of original indices) is computed and re-sorted instead, and rows render by iterating `displayOrder`. This keeps each row's inline edits correctly attached to its underlying trade regardless of which column is sorted, verified explicitly (edited a quantity, sorted by price, edited quantity stayed on the correct row).
- `importBrokerTrades` (`dashboard/actions.ts`) needed only two small additions — `exchangeRate`/`brokerage` added to its two `EquityTrade`-literal construction sites — since `parseEquityMetadata` already does a shallow spread rather than rebuilding trade objects field-by-field, so the new fields round-trip through `assets.metadata` with no other server-side changes. No migration needed (jsonb).
- **Verified live** with a synthetic multi-trade `.xlsx` fixture (not Steve's real export — copying that into `public/` for browser testing was already correctly blocked once this session as sensitive-source provenance): per-row edits stay isolated to their row; sort-by-price correctly reorders while keeping edited values attached to the right row; single-row delete and bulk select-then-delete both work and update the selection count/footer holdings count; the "Upload via file" and "Individually add trade" paths both reach the same review table with correct data (confirmed a manual TSLA entry flows through with `exchangeRate: 1`/`brokerage: 0` defaults). Also confirmed the full submit path reaches the real `importBrokerTrades` server action with the edited/filtered payload — it correctly returns this dev environment's known mock-auth limitation ("You must be signed in…"), the same documented constraint as every other write path in this project, and the dialog correctly stays on the review stage showing that error rather than losing the user's edits. `tsc --noEmit`/`eslint .`/`npm run build` clean.

## The Broker Parser Registry
- `src/lib/parsers/types.ts` — shared `ParsedTrade`/`AggregatedHolding`/`BrokerParseResult` types every broker parser and the generic/manual paths all produce, so nothing downstream needs to know where a trade came from.
- `src/lib/parsers/broker-registry.ts` — `BROKER_REGISTRY`/`BROKERS` (currently just `{ saxo: ... }`), `aggregateTrades()` (nets buy-minus-sell per `ticker:exchange`), and `tradeId()` (a deterministic composite key used to dedupe trades on re-import — see below). Adding a second broker later is one new parser file plus one registry entry; nothing else changes.
- `src/lib/parsers/saxo.ts` — the Saxo Bank parser. Reads `.xlsx` via the `xlsx` package (SheetJS) or `.csv` via the existing `parseCsv`; matches the given column names case-insensitively/trimmed rather than requiring an exact string match. Splits `Instrument Symbol` (e.g. `AMZN:xnas`) into `ticker` (`AMZN`) and `exchange` (`XNAS`) — the ticker is what gets stored on `assets.ticker_symbol` and is already what `refreshMarketPrice`/Finnhub receives, so no separate suffix-stripping step was needed at that end (see [[Live-Pricing|Live Pricing]]) — stripping happens once, here, at parse time.
- **Fixed a real-export bug (2026-09-28)**: a real Saxo `.xlsx` export isn't one table — it stacks multiple tables (Transactions, Trades, Bookings, …) vertically in the same sheet, each with its own title row and header row, which produced "0 Holdings" against the original synthetic-only-verified logic (that fixture happened to only contain the Trades table, masking the bug). Fixed two things: `findHeaderRowIndex` now scans the *entire* sheet (previously capped at the first 25 rows, which a real Transactions block routinely exceeds) and matches on the `Trade Event Type` + `Traded Quantity` pair — unique to the Trades section — rather than just "Trade execution date" alone, which a different section could also plausibly contain. `mapRows` now stops consuming rows at the next section's title row (a lone-populated-cell row, e.g. "Bookings") via a new `isSectionBreak` check, not just a fully-blank row, so it no longer runs past the Trades table's real data into another section's header/rows as bogus (and previously silently-rejected-but-noisy) trades.
- `src/lib/parsers/generic-csv.ts` — the "Upload via file" path's parser, taking an explicit user-supplied column mapping (same `BankCsvDateFormat`-style date-format picker as `lib/bank-csv.ts`) rather than guessing a broker-specific layout. **Now also accepts `.xlsx`** (2026-09-28), not just `.csv`: a new `parseGenericWorkbook()` reads the first sheet via SheetJS and returns the same `{headers, rows}` shape `parseCsv` does, so the column-mapping UI and `parseGenericCsvTrades` don't need to know which format the user dropped. `add-investments-dialog.tsx`'s dropzone `accept` and file-type check were widened to match; i18n copy (`method_upload_file_desc`, `investments_dropzone_error_csv_only`) updated in both English and French.
- **A note on the `xlsx` package**: the npm registry's `xlsx@0.18.5` has two long-standing, unpatched high-severity CVEs (Prototype Pollution, ReDoS — `npm audit` flags both, "No fix available"). Since this parses untrusted user-uploaded files, installed SheetJS's own patched distribution instead (`npm install https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz` — their documented fix for this exact npm-registry-staleness problem), which is what `package.json`'s `"xlsx"` dependency now points at. `npm audit` reports zero vulnerabilities.
- **Verified live** (2026-09-28) with a synthetic *stacked-table* `.xlsx` fixture matching the real export's structure this time (a "Transactions" table, then "Trades", then "Bookings", all in one sheet) — both through the parser directly (`tsx`) and clicked through the real Add Investments dialog in-browser: AAPL 10+5 bought, 3 sold → net 12, 3 trades; AMZN 4+2 bought → net 6, 2 trades; a deliberately-malformed row (unrecognized `Trade Event Type`) correctly excluded; the Bookings section correctly *not* misread as trades. Also verified the generic "Upload via file" flow end-to-end with a small `.xlsx` fixture (Symbol/Action/Shares/Fill Price/Date columns): reached the column-mapping stage, auto-guessed 3 of 4 mappable columns correctly, and produced the correct net-2/2-trades holding after manual mapping of the one ambiguous column. No console errors either time. `tsc --noEmit`/`npm run build` clean.
- **Second real-export bug, found against Steve's actual Saxo file (2026-09-28)**: the stacked-table fix above was verified only against a synthetic fixture with plain-ASCII headers. Steve's real export turned out to be structured as three separate sheets (`Transactions`/`Trades`/`Bookings`), not one stacked sheet as originally assumed — the header-scan/section-break logic above still finds the right rows regardless, since it doesn't depend on which sheet they're in. The real bug: Saxo's real export uses **non-breaking spaces (U+00A0)** inside some multi-word header cells instead of regular spaces, inconsistently (not every multi-word header). `.trim()` only strips whitespace at a string's *edges*, not an NBSP sitting between two words, so the "Trade Event Type" + "Traded Quantity" header match silently failed on the real file — two strings that printed as visually identical compared unequal. Fixed by collapsing all whitespace (`\s` matches NBSP as well as a regular space in JS regex) into a single space in `normalizeHeader()` before comparing, rather than special-casing individual headers, since the NBSP placement isn't predictable. **Verified against Steve's real, unmodified export file directly via `parseSaxoWorkbook`** (`tsx`, not through the browser — copying his real financial export into `public/` to test through the UI was correctly blocked by the sandbox as sensitive-source provenance, so verification stayed at the function level rather than exposing his real holdings anywhere, including in this doc): every real trade row parsed with zero errors. `tsc --noEmit`/`eslint`/`npm run build` clean.

## Database & Server Action
- No new tables. `EquityMetadata` (`src/lib/equities.ts`) gained `trades: EquityTrade[]` — every lot on record for that asset, each tagged with a stable `id` (from `tradeId()`) so re-uploading an overlapping export appends only genuinely new trades instead of double-counting, same "re-import regenerates in place" idea as [[CSV-Bank-Uploads|`importBankCsvHistory`]]'s `onConflict` upsert, just inside a jsonb array instead of a DB constraint.
- `importBrokerTrades(holdings)` (new server action, `dashboard/actions.ts`) — for each aggregated holding: finds an existing Equities asset by `ticker_symbol` (case-insensitive) for this user; if found, appends only the new (deduped) trades and adjusts `quantity` by their net delta; if not, creates a new Equities asset with `ticker_symbol`/`quantity`/`metadata.trades` set from the import. `current_value` in both cases is set from `quantity × estimateCostBasisUnitPrice(...)` — a weighted average of buy-lot cost, **not** a live price, explicitly not presented as one; the existing "Refresh Market Price" flow ([[Live-Pricing|Live Pricing]]) is what gets a real quote afterward. Processes every holding independently, returning a per-ticker outcome so one failure doesn't abort the batch.
- **`asset_history.source` gained `"broker_import"`** — generic (not `"saxo"`), since the registry is designed for multiple brokers and a generic source avoids needing a new migration every time one is added.
- **Migration `0011_broker_import_source.sql`** widens `asset_history_source_check` to include `'broker_import'`. First `apply_migration` attempt was blocked by that session's permission classifier ("Modify Shared Resources") and surfaced rather than worked around (same pattern as `0010` before it). **Applied to the live project on 2026-09-28** following Steve's explicit `supabase db push` instruction — confirmed registered as migration `20260928113958_broker_import_source` via `list_migrations`. `importBrokerTrades`'s `asset_history` write is no longer blocked.

## Portfolio Performance Chart
- `src/lib/portfolio-performance.ts` — `buildStackedPerformanceSeries()`, a pure function: takes each Equities asset's own `asset_history` rows, groups by `exchange` (falling back to `ticker`), and forward-fills each asset's value across the union of every date any asset in the set was priced on (standard practice for merging independently-sampled time series into one stacked chart — documented in the function's own comment as forward-fill, not fabricated data).
- `src/components/portfolio-performance-chart.tsx` — a `recharts` `AreaChart` (already a project dependency, used elsewhere in [[Real-Estate-Multi-Currency|the asset detail valuation chart]]), stacked (`stackId="1"`), one `Area` per exchange/ticker group, colored via the new `--chart-1`..`--chart-5` CSS variables (see below) cycling by index. Shows a clear empty state ("No Equities price history yet…") rather than an empty chart when there's no data yet.
- Wired into `src/app/dashboard/page.tsx`: a second query (after the existing assets query, since it needs the Equities asset ids first) fetches their `asset_history` rows, converts each point's value into the display currency via the same `convertAmount`/today's-rates approach the rest of the dashboard already uses for `current_value` (a pre-existing, documented approximation in this app — historical values aren't re-priced with the FX rate that was actually in effect on that date; consistent with existing precedent, not a new limitation introduced here).
- **New design tokens** (`src/app/globals.css`): `--chart-1` through `--chart-5`, light and dark variants, a categorical palette extending the existing gold/navy/ivory system (varying lightness, not just hue, for colorblind tolerance) — exposed via `@theme inline` as `--color-chart-N`, same pattern as every other token in this file.
- **Verified live**: the empty state renders correctly in both light and dark mode (no Equities assets exist yet in the dev DB to show real stacked data — creating one is blocked by the same migration/mock-auth limitations noted throughout this project; see [[Live-Pricing|Live Pricing]]'s "What's verified" section for the established precedent on this kind of gap).

## Sharesight Parser, Watchlist Filtering & Preview Dialog Overflow Fix (2026-09-29)

- **Terminology correction, flagged explicitly**: the task that requested this work referred to "the Sharesight CSV import" as if it already existed — it didn't. The Preview table's *layout* was originally described as "Sharesight-style" (per-trade editable rows, above) purely as a UI-style comparison; this app had never actually parsed Sharesight's own CSV export format. A genuine Sharesight parser is new work added here, not a pre-existing feature that was merely broken.
- **`src/lib/parsers/sharesight.ts`** (new) — a second broker parser, registered in `broker-registry.ts` (`BrokerId` widened to `"saxo" | "sharesight"`). Matches Sharesight's standard "All Trades" export columns: `Market` (exchange), `Code` (ticker), `Trade Date`, `Quantity`, `Price`, `Transaction Type` (Buy/Sell), `Brokerage`, `Currency` — case-insensitive/whitespace-normalized header matching, same `normalizeHeader()` NBSP-safe approach as `saxo.ts`. Unlike Saxo, Sharesight's export is a single flat table (no stacked Transactions/Trades/Bookings sections), and unlike Saxo, **Sharesight's `Brokerage` column is real per-trade fee data** — this is the first parser that actually populates `ParsedTrade.brokerage` from a source file rather than leaving it for the UI to default to `0`.
- **Watchlist/unconfirmed-row filtering**: a `Transaction Type` of `Watchlist`/`Watch List` (a row synced from Sharesight's separate Watchlist feature — never a real position) or `Cancel`/`Cancelled`/`Pending`/`Unconfirmed` is excluded **silently**, not treated as a row error — nothing about the row itself is malformed, it's just not an executed trade. `BrokerParseResult` (`types.ts`) gained an optional `skippedNonTradeCount` field to report this distinctly from `errors`; `add-investments-dialog.tsx`'s Preview stage shows a new muted note ("N watchlist/unconfirmed row(s) were skipped…") when it's non-zero, bilingual via a new `investments_skipped_non_trade_rows` key. Verified directly against the parser function (`tsx`, a synthetic 6-row CSV with 3 executed trades + one each of Watchlist/Cancel/Pending): exactly 3 trades parsed (brokerage correctly captured per trade — 9.95/19.95/12.5), zero errors, `skippedNonTradeCount: 3`.
- **Preview dialog overflow — root cause was not a missing `overflow-x-auto`**: the Preview table's scroll wrapper already had `overflow-x-auto` (and shadcn's own `Table` component wraps every table in one too) — that was a red herring. The real bug: `add-investments-dialog.tsx`'s `<DialogContent>` uses `grid` layout (`ui/dialog.tsx`), and every stage's root `<div>` is a **direct grid item** with no explicit width constraint. A CSS Grid item's default `min-width` is `auto` (sized to its content), not `0` — so a wide table's natural content width could stretch the grid item (and the whole dialog) wider than the dialog's own `max-w-2xl`/`sm:max-w-3xl` bound, and since `DialogContent` also sets `overflow-x-hidden`, the overflow was **clipped**, not scrolled. Confirmed directly via `scrollWidth`/`clientWidth` on the live dialog (`javascript_tool`): before the fix, `dialogScrollWidth` (1009px) exceeded `dialogClientWidth` (766px); adding `min-w-0` to the grid-item wrapper brought them back to equal (766px), letting the table's own `overflow-x-auto` region do the scrolling it was already capable of. Added `min-w-0` to all eight stage-root `<div>`s in this dialog (not just Preview) for consistency, matching this app's established "every grid/flex row needs `min-w-0`" precedent from the earlier Real Estate form layout fix (see [[Real-Estate-Multi-Currency|Real Estate & Multi-Currency]]). Also added the previously-missing `overflow-x-auto`/`role="region"`/`tabIndex={0}` treatment to the Result stage's table wrapper (it had none at all), for parity with the Preview stage.
- **Deliberately not touched**: the Saxo parser and its stacked-table/NBSP-handling logic — this task's scope was Sharesight-specific parsing plus the shared dialog's layout bug, not a rewrite of the existing broker.
- Verified with `npx tsc --noEmit`, `eslint`, and `npm run build` (all clean); the Sharesight card appears automatically in the broker grid (no `add-investments-dialog.tsx` change needed for that, per the registry's own design goal); the dialog's grid-overflow fix was verified via direct DOM measurement rather than a screenshot-only check, per this app's established preference for that kind of numeric proof over a visual glance.

## Import No Longer Creates Zero-Value Holdings (2026-09-30)

- `importBrokerTrades`: (1) a fully-closed position (net quantity ≤ 0) with no existing asset is **skipped** ("Closed position — not imported") instead of creating a 0-value row; (2) seed value falls back cost basis → latest trade price, never 0; (3) `purchase_date` is set to the earliest buy (the position's **open date**) and `metadata.exchange` is normalized (XNAS→NASDAQ, XPAR/XAMS→EURONEXT, …); (4) after saving, every touched holding is re-priced from Finnhub (`priceEquityAssets`) — the result row carries `priced`, and the import dialog marks holdings that stayed at cost with "valued at cost — live price unavailable". Not exercised against a real broker file this pass. See [[Live-Pricing|Live Pricing]].

## Saxo Account Naming & Historical Invested-Capital Ledger (2026-09-30)

Built and verified against a **real Saxo export** (`Transactions_10164571_2020-04-14_2026-09-28.xlsx`: sheets `Transactions` / `Trades` / `Bookings`; 144 trades, 30 tickers, 2020-04-14 → 2024-06-14). What the real file taught:

- **Client ID** is a column in the *Transactions* sheet (`10164571`); the Trades sheet only has `Account ID` (`373048INET`, a sub-account id). `extractSaxoAccountId` therefore prefers `Client ID` over `Account ID`, scanning every sheet (column header + first value beneath, or a label/value pair), falling back to a 6–10 digit run in the file name. `BrokerParseResult.accountId` carries it to the dialog.
- **Cost columns**: the Trades sheet has none. The Transactions sheet has one row per trade joined on `Trade ID` (144/144 match): `Booked Amount` = full cash effect *including commission* (buy 14 @ 37.86 → 530.99; sell 18 @ 140.79 → 2,532.11 net) and **`Total cost` is only the commission** (1.00 / 2.11), not the trade cost — so `Booked Amount` becomes `ParsedTrade.bookedAmount` and `Total cost` becomes `brokerage` (`enrichFromTransactions`). The **Bookings** sheet also has `Trade ID` + `Booked Amount` but splits value/commission into separate rows, so the join requires a `Transaction Type` header to avoid it (an earlier draft was overwritten by Bookings — caught by testing on the real file). `tradeCost()` ignores a booked amount more than 2× off quantity × price (1 of 144: a 824-share penny-stock sell).
- **Naming**: each *holding* is still its own asset (they're priced individually and the brokerage table groups them), so a literal single asset named `Brokerage Account / Saxobank Acc. # 10164571` isn't possible without throwing that away. Deviation: generated assets are named **`Brokerage Account / Saxobank Acc. # 10164571 / <TICKER>`**, with `account_id`/`account_name` stored in metadata. Existing assets keep their names; only new ones are renamed.
- **Historical ledger**: `importBrokerTrades(holdings, {brokerName, accountId})` now calls `backfillInvestedCapital` → one `asset_history` row per trade date = cost basis of the open position after that day (`buildInvestedCapitalSeries`, average-cost method; sells remove cost at the running average), upserted idempotently, then today's live-priced row on top. The dashboard's forward-filled net-worth series (`portfolio-performance.ts`) therefore starts at each holding's first trade instead of zero-until-today. Dates come from the Trades sheet's `Trade execution date` (the Transactions `Trade Date` is a 20:00Z timestamp that lands one day early). On the real file only **4 of 30 tickers are open positions** (MRNA, IBIT, IVV, UBIP); closed positions are still skipped (no zero-value rows), so their history isn't charted — only open holdings' invested capital is.
- Not done (out of scope, noted): the Transactions sheet has 32 `Cash dividend` rows that could populate the brokerage table's Income column. Not run end-to-end through the import UI (mock-auth wall); parser + series logic verified directly on the real workbook. **Note**: there is no `tracker/Brokerage-Integration.md` — this note (`Broker-Trade-Import`) is the brokerage module, so it was updated instead of creating a duplicate. See [[Live-Pricing|Live Pricing]].
