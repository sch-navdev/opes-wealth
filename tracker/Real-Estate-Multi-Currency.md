## All-In Cost Basis, Fee-Aware Net Gain & Currency-Explicit Inputs

## Auto-Generated Historical Timeline

- `src/app/dashboard/actions.ts` gained `syncAssetHistory(supabase, assetId, currentValue, categoryName, metadata)`, called from both `addAsset` and `updateAsset` after the insert/update succeeds (both now `.select("id, asset_categories(name)")` so the category name is available without an extra round-trip). It upserts a set of `asset_history` rows keyed by `recorded_date`:
  - For Real Estate assets with a `payment_schedule`: a starting point on the **earliest milestone's due date** — there's no dedicated "purchase date" field in `RealEstateMetadata`, so the down-payment milestone's date stands in for the purchase/contract date, valued at that milestone's amount plus every fee (ADM, notary, agency, renovation, furnishing) — and one point per milestone marked `"paid"` (in date order), valued at the running cumulative-paid total (plus the same fees) up to that date. Unpaid/pending milestones are skipped.
  - A point for **today**, valued at the market valuation (`metadata.market_valuation`, falling back to the asset's stored value) with `net_equity` set to the asset's actual `current_value` column (already net of any linked loan/off-plan balance).
  - **Field-name note**: the request said to sort by `recorded_at` — the actual column (from `0001_initial_schema.sql`) is `recorded_date`; used the real column throughout.
  - **Design simplification, flagged clearly**: for the historical (non-today) points, there's no recorded market valuation at each past date — only cumulative cash invested. Rather than inventing a fictitious historical market curve, both `value` and `net_equity` are set to that same cumulative-cash-invested figure for those points. Only today's point has a real value/net-equity split. This means the chart's "Market Value" and "Net Equity" lines overlap until very recently, then diverge — an honest reflection of what data actually exists, not a bug.
  - Non-Real-Estate assets just get the "today" point (no purchase-date/milestone concept applies to them).
- `supabase/migrations/0007_asset_history_unique_date.sql` — adds a `unique (asset_id, recorded_date)` constraint so `.upsert(rows, { onConflict: "asset_id,recorded_date" })` works; re-saving an asset's form regenerates the same dated points instead of duplicating them (e.g. editing the down-payment milestone's amount updates that one row in place). Syntax-checked with `libpg-query` (installed temporarily, removed after). Not yet applied to the live database.
- `asset-detail-view.tsx`'s `chartData` now explicitly re-sorts `history` by `recorded_date` before mapping (defensive — `page.tsx`'s query already orders ascending, but the component no longer assumes that). The X-axis and tooltip both use a new `formatChartDate()` (`Intl.DateTimeFormat("en-GB", { day: "2-digit", month: "2-digit", year: "numeric" })` → `DD/MM/YYYY`) instead of showing the raw ISO date string.
- Verified two ways: a standalone Node dry-run of the exact cumulative-fee/milestone algorithm against a 3-milestone example (down payment + fees, one more paid milestone, one pending milestone skipped, today's split value/net-equity) confirmed the arithmetic; and a disposable preview route rendering the resulting 3-point history through the real chart component confirmed the X-axis renders `15/01/2026` → `15/05/2026` → `21/09/2026` and the area chart correctly spans the full purchase-to-today range.
- Not yet verified against a live Supabase instance — the actual `upsert`/`onConflict` round-trip (and whether the `0007` migration's unique constraint applies cleanly) hasn't been exercised end-to-end.

## Consolidated Registration Fee (Notary / RERA / ADM)

## Aperçu Graph Anchored to Purchase Date

- **Problem being fixed**: the Aperçu chart's `chartData` plotted every stored `asset_history` row as-is — nothing stopped a stray or back-populated point from before the asset's `purchase_date` from showing up, and a standard (non-off-plan) purchase's very first point was whatever market valuation the user typed in at creation time, not the actual all-in cost basis (purchase/contract price + acquisition fees) established in the earlier cost-basis work above.
- `asset-detail-view.tsx` — `chartData`'s construction now goes through an intermediate `displayHistory` step, Real Estate only (gated on `isRealEstate`):
  1. Sorts `history` ascending (`sortedHistory`, unchanged from before).
  2. If `asset.purchase_date` is set, filters out every point with `recorded_date < purchase_date`.
  3. For **standard (non-off-plan) purchases only**, pins whatever lands exactly on the purchase date to `{ value: totalCost, net_equity: totalCost }` (`totalCost` = the existing `calculateTotalCost` figure), overwriting it if a stored row is already there, or prepending a synthetic `id: "purchase-anchor"` point if not. **Off-plan properties are left alone** beyond the date filter — their earliest point is already the down-payment milestone (`syncAssetHistory`'s existing logic), which is a more accurate anchor than the full contract price, since that isn't paid at signing.
  4. If `asset.purchase_date` is falsy (an asset saved before it became a mandatory field), none of the above runs and the full unfiltered `sortedHistory` is shown — the required graceful fallback to "earliest available history."

## Tenancy Rework: Real-PDF Parser Fix, Multi-Contract History, Property Expense Ledger (2026-09-29)

Driven by real QA against a genuine Ejari export (Ellington House Unit 713) — the original tenancy pass above (2026-09-29 entry) was verified only against a hand-written synthetic sample, which turned out not to match the real document's layout at all.

- **Root cause of the parsing bugs**: `lib/tenancy-parser.ts`'s original `extractAfterLabel()` assumed a value follows its label on the same or next line. Ejari's actual `pdf-parse` output instead keeps each label on its own line, with the *value* line for a paired field (Start/End Date, Contract/Annual Amount) holding **both** column values concatenated together with a mirrored Arabic label in between — e.g. the line under "Start Date" is `21-11-2025<Arabic "Start Date" label>01-12-2026`, where the **second** date belongs to "End Date" (the label appearing *after* that line), not the first. The old code's same-line regex found nothing for these paired fields (hence blank Annual Rent/End Date) and, for Tenant Name, never separated the mangled Arabic transliteration from the real English name.
- **Rewrote `lib/tenancy-parser.ts`** entirely against the real extracted text (captured via a disposable `pdf-parse` script, not guessed): `lineAfterLabel()` anchors on an exact label line and reads the line immediately after it; `extractEnglishName()` pulls the longest run of Latin uppercase letters out of a mixed Arabic/English line (the Arabic glyphs in this PDF's font encoding never form a long ASCII-uppercase run, so this reliably isolates the real name); date/amount extraction pulls **all** tokens matching their pattern off the shared value line and assigns first→the label above, second→the label below, matching the row-pairing structure exactly. Verified against the real PDF text: tenant name `CHESTER STEPHEN SCOTT` (Arabic dropped), start date `2025-11-21`, end date `2026-12-01`, contract value `267,123.00`, annual rent `259,202.91` — all five now match the source document exactly.
- Tawtheeq (Abu Dhabi) has no real sample available yet, so it mirrors the same row-pairing/name-extraction logic as a best-effort analogy rather than a verified fix — flagged in its doc comment.
- **Tenancy contracts are now a list, not one flat set of fields**: `RealEstateMetadata.tenant_name`/`tenancy_start_date`/`tenancy_end_date`/`tenancy_contract_value`/`annual_rent` are replaced by `tenancy_contracts: TenancyContract[]` — a property is re-let contract after contract (2025-2026, then 2026-2027, etc.), and importing a new PDF now **appends** a new entry instead of overwriting the last one. `parseRealEstateMetadata` migrates any pre-existing flat-field data into a single legacy array entry on read, so no data already saved under the old shape is lost. `findActiveTenancyContract(contracts, date)` picks the contract in effect for the Rental Yield calc (falls back to the most recently started one if none currently applies). New `deleteTenancyContract` server action, exposed as a delete button per contract card in the Tenancy tab (each labeled by its start/end year, e.g. "2025 – 2026").
- **Property expenses are now a dated ledger, not one "monthly" figure**: `monthly_property_expenses: number | null` is replaced by `property_expenses: PropertyExpense[]` (`{id, description, date, amount}`), added one at a time via an inline form in the Tenancy tab (new `addPropertyExpense`/`deletePropertyExpense` server actions) and summed with `sumPropertyExpenses()`. Monthly Net Rent no longer subtracts a flat expense figure (gross rent − current loan installment only); the running expense total is instead subtracted once, as a lump sum, from Net Profit (incl. rental income) — and every individual expense also feeds the Property IRR as its own dated cash flow, more precise than the old flat monthly-rate approximation.
- The old flat Tenancy fieldset was removed from `real-estate-fields.tsx` (the Add/Edit dialog) — tenancy data now only flows through the array-based system above (PDF import or the Tenancy tab), which doesn't fit a single-entry manual form anymore.
- Verified: the corrected parser's output checked directly against the real PDF's extracted text (exact match on all five fields, see above); the new list UI verified live in the browser against the existing seeded asset — the legacy-migration path correctly surfaced its one pre-existing (stale, pre-fix) contract as a deletable card, the "Add Expense" form's client-side validation blocked an empty submission with a localized message, and both the delete-contract and add-expense actions correctly reached their real server actions (surfacing the standard mock-auth "must be signed in" message, same as every other write path in this project). `npx tsc --noEmit`, `eslint`, and `npm run build` all clean.

## Amortization Engine: Day-1/Pre-First-Installment Balance Bug (2026-09-29)

Flagged by Steve from a live chart tooltip: the Valuation History graph's Day 1 point showed Equity exactly equal to Market Value (i.e. the loan appeared fully absent), and asked to double-check the whole Equity curve tracks the amortization schedule correctly, plus asked for a visible loan-balance line to check it against directly.

- **Root cause** (`lib/amortization.ts`'s `getOutstandingPrincipalAt`): for any date strictly after `loan.start_date` but before the *first* amortization entry (one month later), the lookup loop found no schedule entry with `date <= isoDate` to assign a balance from, and fell through to its initializer — which was `0`, as if the loan had already been paid off. Ellington House's purchase date (2025-10-06) falls exactly in that gap after its loan's start date (2025-10-01), so the Day 1 chart point always showed Equity = Market Value (the full 2,720,000 AED loan silently dropped from the calculation) instead of Market Value − full principal.
- **Fix**: that initializer is now `loan.amount` (the full original principal — correct, since no installment has been paid yet), not `0`. This is a general fix, not anchor-point-specific: it also corrects `getOutstandingPrincipalAt` for the top-level Equity figure, the Financing card, `dashboard/page.tsx`'s liability aggregation, and every other caller for any asset whose purchase date (or any queried date) falls in that same start-date-to-first-installment window.
- **Verified directly against the live database** (a disposable script reading the real asset + `asset_history` rows via the service-role key, running the exact same calculation the chart does): Day 1 (2025-10-06) now correctly shows `loanBalance: 2,720,000` → `netEquity: 680,000` (previously `netEquity: 3,400,000`, the bug); every subsequent point shows the loan balance monotonically decreasing (2,720,000 → 2,677,831 → 2,671,727 → 2,665,602 → 2,659,457 → 2,653,291) as expected, and the final computed Equity (646,708.42) matches the asset's live top-level Net Equity figure exactly.
- **Unrealized Gain confirmed unaffected and correct by design**: it's `Market Value − Total Cost Basis`, which never involved the loan at all — Day 1 correctly shows `-226,620` (the acquisition fees), matching the original spec example exactly.
- **New chart series**: the Valuation History graph gained a 4th line, Outstanding Loan Balance (`getOutstandingPrincipalAt` per point, dashed, a new chart color), gated on `loanIsAmortizable` — plotted alongside Market Value and Equity so the two can be visually cross-checked (Equity = Market Value − Loan Balance at every point) rather than trusted blindly.
- `npx tsc --noEmit`, `eslint`, and `npm run build` all clean.
