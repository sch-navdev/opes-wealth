## Password Complexity & Email Verification UI
- **Password complexity**: new `src/lib/auth-validation.ts` — a Zod `passwordSchema` (min 8 chars, one uppercase, one lowercase, one number, one special character) and `getPasswordRequirementErrors(password)`, which returns every unmet rule's message (Zod collects all failing checks for a chained string schema, not just the first). `login-form.tsx`'s Password field is now controlled; in sign-up mode it renders the unmet requirements as an inline list once the field has been touched, and `handleSubmit` blocks the server action entirely on any unmet rule (mirroring the existing Confirm Password mismatch guard). `signup()` in `auth/actions.ts` also re-validates server-side with the same schema (defense in depth — a client can always be bypassed) before calling `supabase.auth.signUp`.
- **Email verification UI state**: `signup()` now inspects Supabase's response — `data.user` present but `data.session` null means the project requires email confirmation before a session exists. - **Email callback route**: `src/app/auth/callback/route.ts` (new) — a Route Handler that reads the `code` query param from Supabase's confirmation link, calls `exchangeCodeForSession(code)`, and redirects to `/dashboard` on success (or `/login?error=...` on failure). `signup()`'s `emailRedirectTo` now points at `${getSiteURL()}/auth/callback`.
- **`getSiteURL()` (new, in `auth/actions.ts`)**: prefers `NEXT_PUBLIC_SITE_URL`, falls back to `https://${VERCEL_URL}`, falls back to `http://localhost:3000`. **Important**: this project has Vercel SSO Protection enabled on non-custom-domain deployment URLs (confirmed via the Vercel MCP) — a raw `VERCEL_URL` redirect would land a verifying user on Vercel's auth wall instead of the app, so `NEXT_PUBLIC_SITE_URL` needs to be set explicitly. ## Crash Report Follow-Up (Could Not Reproduce; Hardened Anyway)
- **Reported**: the live Vercel deployment crashed to Next.js's generic error boundary on `/login` right after sign-up, right after `NEXT_PUBLIC_SITE_URL` was updated to the custom domain (`https://www.opeswealth.app`).
- **Investigation**: Vercel's `get_runtime_errors`/`get_runtime_logs` MCP tools both returned `403 Forbidden` for this project/account (a plan/permission limit, not something fixable from here). Reproduced the exact flow directly against `https://www.opeswealth.app` instead (fill form, submit, wait) — it completed successfully with the correct "check your email" screen, no console errors, no crash. **Could not reproduce the reported crash.** Most likely explanation: the custom-domain env var change hadn't been baked into a build yet at the moment it was tested (`NEXT_PUBLIC_*` vars are inlined at *build* time, so saving a new value in the Vercel dashboard doesn't take effect until the next deployment) — but this is a plausible explanation, not a confirmed root cause.
- **Hardened anyway**, since defensive error handling here is good practice regardless of whether this specific crash reproduces:
  - `auth/actions.ts` — `login()`'s `signInWithPassword` call and `signup()`'s `signUp` call are now each wrapped in their own `try/catch`, returning a generic `{ error: "..." }` on an unexpected throw instead of letting it propagate. Neither `try` block wraps a `redirect()` call, so Next's internal redirect-signal throw is never at risk of being caught here.
  - `login-form.tsx` — the submit handler's `startTransition` callback is now wrapped in `try/catch` too, but explicitly re-throws anything matching Next's redirect-error shape (`digest` starting with `"NEXT_REDIRECT"`) via a new `isNextRedirectError()` helper — a blanket catch here would otherwise silently swallow a successful login's navigation, a well-known Next.js Server Action gotcha. Real errors are caught and shown as inline text via the existing `error` state.
  - Explicit return-type annotations on `login()`/`signup()` (added in the original implementation) already resolved a TS inference ambiguity around their return types — not related to this crash, but worth noting they're intentional, not incidental.
- **Verified**: `tsc --noEmit` and `next build` both clean. Locally, a real Supabase error (`email rate limit exceeded`, hit from testing too many signups in a short window) correctly rendered as inline text with no crash and no console errors — the exact failure mode the hardening targets. A bad-credentials login also correctly showed "Invalid login credentials" inline. Could not test a real successful-login redirect against production credentials (none available in this environment), so the redirect passthrough is verified by code review/construction, not an observed successful redirect.
- **Test accounts**: debugging this created two more unconfirmed test users in the live Supabase project (`opeswealth-verify-test@mailinator.com`, `opeswealth-debug-test@mailinator.com`, both disposable inboxes) — combined with the one from the previous session, there are now several test accounts pending cleanup.

## Password Reset MFA Step-Up
- **Why**: `supabase.auth.updateUser({ password })` requires the session to be at aal2 when the account has an MFA factor enrolled — a recovery-link session only ever authenticates at aal1, so an MFA-enrolled user hitting `/reset-password` would previously get an opaque Supabase error from `updateUser` instead of a usable flow.
- `src/components/reset-password-form.tsx` — on mount, calls `supabase.auth.mfa.getAuthenticatorAssuranceLevel()` (browser client) and hides the New/Confirm Password fields whenever `currentLevel === 'aal1' && nextLevel === 'aal2'`. While hidden, renders a 6-digit TOTP input; submitting it finds the enrolled factor via `listFactors()`, opens a `challenge()`, and `verify()`s the code — the same three-call sequence as `verifyMfaLogin()` in `auth/actions.ts`, just done client-side here since this form already talks to the browser Supabase client rather than a server action. Password fields render once verification succeeds (or immediately, if no step-up was needed).
- Left `router.push("/dashboard")` on successful password update as a relative path, not an absolute `https://www.opeswealth.app` URL — that's same-origin client-side navigation via `next/navigation`, not a Supabase-generated email link. The absolute-URL requirement documented above (`PRODUCTION_SITE_URL`/`getSiteURL()`) exists specifically to dodge Vercel's SSO wall on server-generated `emailRedirectTo` links; hardcoding the production domain into client-side `router.push` would instead break local dev and preview-deployment testing.
- **Not verified end-to-end**: no real recovery-link session + enrolled TOTP device available in this environment. `tsc --noEmit` clean; the non-MFA path (password fields render immediately) is unchanged from the already-verified flow in the previous entry below.
