# Market Data Integration

**Status:** Phase 1 Step 9 (Live Pricing) built and deployed as a **stubbed** pipeline — real, working plumbing end-to-end (Edge Function, adapter, UI, DB persistence) but the actual ADREC/DARI provider call is a clearly-marked mock, not a real one. See "Step 9 — Live Pricing (stubbed)" below. The rest of this note is the original design-only outline that preceded it and is still accurate about what remains unconfirmed.

## Honesty check before anything else
I don't have confirmed, current documentation for a public ADREC (Abu Dhabi Real Estate Centre) or DARI developer API — access terms, authentication method, endpoint shapes, and rate limits are all **unconfirmed**. These are the kind of government/institutional property-valuation indices that often require a direct partnership or registered-developer agreement rather than a self-serve public API. Before writing any real integration code, someone needs to confirm directly with the provider: (1) that a programmatic API exists at all, (2) its auth model, (3) its terms of use for a commercial wealth-tracking product. Nothing below should be read as "this endpoint exists" — it's the shape the integration would take *once* those facts are confirmed, designed to slot into what's already built.

## Where this already has a landing spot in the app
- `asset_history.source` (migration `0006`) already accepts `'manual' | 'dari' | 'dubailand'` — added specifically so a future automated valuation could be tagged apart from a manual entry, without a schema change.
- The Refresh Valuation dialog (`asset-detail-view.tsx`) already has a Source dropdown with DARI/Dubai Land Department options, currently just tagging the string on a manually-entered number — see the existing "No live DARI or Dubai Land Department integration is configured yet" copy in that dialog.
- `updateAssetValuation()` (`src/app/dashboard/actions.ts`) is the single write path for a new valuation + `asset_history` row, for both manual and (eventually) automated updates.

## Proposed architecture
1. **Adapter module** — `src/lib/market-data/dari.ts` exporting one function: `fetchDariValuation(propertyRef: string): Promise<{ value: number; asOf: string; raw: unknown }>`. Internal HTTP/auth details stay inside this one file so the provider can be swapped or the API version bumped without touching call sites.
2. **Normalized interface, not a DARI-specific one** — define a `MarketDataProvider` type (`{ fetchValuation(propertyRef: string): Promise<...> }`) so `dari.ts` is one implementation of it. If Dubai Land Department's own feed also becomes available later (the UI already has a slot for `'dubailand'` too), it becomes a second adapter behind the same interface, not a special case.
3. **Trigger point** — most likely a manual "Refresh from DARI" action next to the existing "Refresh Valuation" dialog (calls the adapter, then reuses the *existing* `updateAssetValuation(assetId, value, 'dari')` path — no new write logic needed), rather than a background cron job, at least initially: automated recurring valuation pulls raise their own questions (cost per call, provider rate limits, whether a stale property reference silently returns wrong data) that are easier to reason about with a human triggering each refresh.
4. **Credentials** — if the provider requires an API key, it's a server-only secret (never `NEXT_PUBLIC_*`), read only inside the adapter module, following the same pattern as `SUPABASE_SERVICE_ROLE_KEY` in [[Authentication-Security|Authentication & Security]] — never exposed to the client bundle.
5. **Property reference** — DARI/ADREC valuations are keyed by a specific property identifier (parcel/plot number or title deed number), which isn't currently a field on `RealEstateMetadata`. That would need adding (a `dari_property_ref` or similar field in `src/lib/real-estate.ts`, following its existing pattern) before any real call could be made — not done here since this task is design-only.
6. **Failure handling** — the adapter should fail loudly with a specific error (property not found vs. auth failure vs. network error) rather than silently falling back to the manual figure, so a bad automated pull never quietly overwrites a correct manually-entered valuation.

## Step 5 — Dubai Land Department / RERA Integration (stubbed, built 2026-09-29)

Same honesty caveat as the section above, restated for this specific service: **no confirmed public API exists yet** for DLD's Smart Valuation, Oqood & TAS Project Status, or Ejari Rental Index endpoints — everything below is the real, final request/response contract with a clearly-marked mock (`isMock: true`) standing in for the actual provider call, built on explicit request following the same "stubbed pipeline" pattern as DARI (Step 9 above). Nothing here should be read as a working DLD/RERA integration.

- **`src/lib/services/dld-client.ts`** (new) — a **different architecture from DARI's Edge-Function shape**, per this task's explicit request: a plain server-only TypeScript module (no Supabase Edge Function), imported directly by `dashboard/actions.ts` (a `"use server"` file) rather than invoked over `supabase.functions.invoke`. Exports three subsystem functions, each returning a `{ ok: true, isMock, ...data } | { ok: false, code: DldErrorCode, error }` union:
  - `getSmartValuation({ titleDeedNumber, plotId })` → `{ ai_valuation_amount, valuation_date, certificate_reference }` (ready-built properties).
  - `getOqoodProjectStatus({ oqoodContractNumber?, projectNumber?, escrowId? })` → `{ completion_percentage, escrow_balance_status, latest_inspection_date }` (off-plan properties). **Deliberately no monetary figure** — Oqood/TAS's real API doesn't return one, so this integration doesn't fabricate a valuation from it (see the Action Wiring note below).
  - `getEjariRentalIndex({ propertyType, communityId, bedroomCount })` → `{ index_rental_range: { min, max }, max_permissible_increase }` (rental benchmark; wired into the client module but **not yet called from any UI/action** — no Refresh-style trigger exists for it, since nothing in this task's scope needed one yet).
  - **OAuth 2.0 client-credentials grant with in-memory token caching**: `getAccessToken()` caches `{ accessToken, expiresAt }` at module scope (safe under Next.js's long-lived Node process, unlike a stateless Edge Function), refetching ~30s before expiry. Reads `DLD_CLIENT_ID`/`DLD_CLIENT_SECRET`/`DLD_TOKEN_URL`/`DLD_API_BASE_URL` (optionally `DLD_OAUTH_SCOPE`) via plain `process.env` — safe here specifically because this module is never imported from a `"use client"` file, unlike `NEXT_PUBLIC_*` vars which do leak to the browser bundle.
  - **Mock mode**: `DLD_MOCK_MODE=true`, or simply missing `DLD_CLIENT_ID`/`DLD_CLIENT_SECRET`, makes every subsystem function return a deterministic mock (seeded by hashing the request's identifiers, so the same inputs always produce the same mock figure) instead of attempting a real call — this is the actual state until real DLD credentials exist.
  - `DldErrorCode` union (`invalid_request`, `invalid_deed_number`, `invalid_project_number`, `inactive_project`, `not_found`, `rate_limited`, `provider_not_configured`, `invalid_response`, `timeout`, `network_error`) thrown as a `DldServiceError` internally, caught once in a shared `withErrorHandling()` wrapper. `invalid_deed_number`/`invalid_project_number`/`inactive_project` are defined but not yet distinguishable from a generic provider response in mock mode (there's no real API to return them) — they exist so the real integration can map actual DLD error responses onto them without a contract change.
- **Metadata schema** (`src/lib/real-estate.ts`) — `RealEstateMetadata` gained six new identifier strings (`title_deed_number`, `plot_id` — "Municipality Plot ID / Area ID" as one combined field, matching the task's own slash-separated naming — `oqood_number`, `project_number`, `escrow_id`, `community_id`) plus three off-plan project-status fields (`completion_percentage: number | null`, `escrow_balance_status`, `latest_inspection_date`), all defaulted empty/`null` in `EMPTY_REAL_ESTATE_METADATA`. **No new field for bedroom count or property type** — Ejari's request reuses the existing `rooms`/`propertyType` fields rather than duplicating them under new names.
- **Form** (`real-estate-fields.tsx`) — new "Dubai Land Department / RERA Identifiers" panel (fully bilingual via `t()`, following the Linked Loan panel's precedent from the mortgage-liability task): shows Title Deed Number + Plot/Area ID for a standard purchase, or Oqood Contract Number + Project Number + Escrow ID for an off-plan one (gated on `is_offplan`, same toggle the rest of the form already keys off), plus a Community ID field shown either way (rental benchmarking applies regardless of build status). New `TextField` helper added alongside the existing `NumberField`/`ToggleField` for these plain-string inputs.
- **Action wiring** (`src/app/dashboard/actions.ts`) — new `refreshDldValuation(id)`, explicit discriminated return type `RefreshDldValuationResult` (two `ok: true` shapes by `kind`, one `ok: false` with an optional `DldErrorCode`). Looks up the asset, confirms it's Real Estate, then dispatches on `metadata.is_offplan`:
  - **Ready-built** → `getSmartValuation()`, then **reuses the existing `updateAssetValuation(id, value, "dubailand", date)`** (no new persistence logic) — which already recomputes Net Equity via `resolveOutstandingLoanBalance` (from the mortgage-liability task above) and upserts `asset_history`. `calculateTotalCost`/`calculateUnrealizedGain` are then called on the result to hand the UI an immediate cost-basis/gain figure without waiting for a full page reload.
  - **Off-plan** → `getOqoodProjectStatus()`, then writes `completion_percentage`/`escrow_balance_status`/`latest_inspection_date` straight into `metadata` via a plain `.update()`. **Deliberately does not touch `assets.current_value`/`asset_history`** — the task's own instructions say to "update `current_value` and log a new valuation point" for both branches, but Oqood/TAS's real output has no monetary figure at all (only progress/escrow/inspection data per the task's own subsystem spec); inventing a valuation from a completion percentage would be fabricated data, not a valuation refresh, so this branch is scoped to what the API actually returns. Flagging this explicitly as a deliberate deviation from the literal instruction, for the same reason DARI's stub never claims to be a real provider call.
- **UI** (`asset-detail-view.tsx`) — a "Refresh from Dubai Land Department" icon button (`Landmark`, next to DARI's `CloudDownload` and the manual `RefreshCw`), Real Estate only, behind the same `AlertDialog` confirmation pattern as DARI. Unlike DARI's raw-string errors, this one follows the more robust `MARKET_PRICE_ERROR_KEYS` pattern (a `DLD_ERROR_KEYS: Record<string, TranslationKey>` map, all-new bilingual keys) — a deliberate choice for a brand-new integration rather than copying DARI's less-robust precedent. The Analyse tab's off-plan section gained a small read-only "Project Status" card (completion %, escrow status, latest inspection date), and the Paramètres spec view gained a "DLD Identifiers" card mirroring the form's off-plan/ready-built split.
- Verified with `npx tsc --noEmit`, `eslint`, and a full `npm run build` (all clean); not verified in a live browser/Supabase round-trip in this session.

## Mock DLD/ADREC Data Is Read-Only (2026-09-30)

- **Rule**: any DLD or ADREC result with `isMock: true` (sample mode — no credentials configured) is returned to the UI for display and certificate preview but **never written to the database**. `refreshDldValuation` and `refreshAdrecValuation` now skip `updateAssetValuation` (which overwrites `assets.current_value`, `metadata.market_valuation` and inserts an `asset_history` row) and the off-plan project-status `assets.metadata` update whenever the provider result is mock. Both results carry `persisted: false`, and the UI says "Sample data … shown for preview only and was NOT saved". Live (non-mock) results persist exactly as before. The display-only `getAdrecLiveValuation`, the `adrec-pricing` Edge Function and `getDldCertificate` never wrote anyway.
- **Why**: a sample-mode DLD refresh on 2026-09-30 replaced Ellington House 1 - 713's valuation (3,300,000) with a fabricated 2,728,506, dropping Equity to ~75k and making Net Profit hugely negative.
- **Note on naming**: the table is `asset_history` (there is no `valuation_log` table — "Valuation Log" is just the UI label for its rows).
- **Existing bad data — one-off cleanup, NOT yet run**: the only affected row in the live DB is `asset_history.id = 30830335-aa64-47e0-824b-ff32e62fc7cd` (`dubailand`, 2,728,506, 2026-09-30). The automated attempt to delete it was blocked by the session's permission check, so it must be run manually (Supabase SQL editor). Deleting the row alone is not enough — the mock refresh also overwrote the asset itself, so the same statement restores `current_value` and `market_valuation` from the latest remaining history point (2026-09-29: value 3,300,000, equity 580,000):

```sql
with d as (
  delete from asset_history where source = 'dubailand' and value = 2728506 returning id, asset_id
), latest as (
  select distinct on (h.asset_id) h.asset_id, h.value, h.net_equity
  from asset_history h
  where h.asset_id in (select asset_id from d) and h.id not in (select id from d)
  order by h.asset_id, h.recorded_date desc
)
update assets a
set current_value = l.net_equity,
    metadata = jsonb_set(a.metadata, '{market_valuation}', to_jsonb(l.value))
from latest l
where a.id = l.asset_id
returning a.id, a.name, a.current_value, a.metadata->>'market_valuation';
```
