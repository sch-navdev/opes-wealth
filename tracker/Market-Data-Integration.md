# Market Data Integration

**Status:** Phase 1 Step 9 (Live Pricing) built and deployed as a **stubbed** pipeline — real, working plumbing end-to-end (Edge Function, adapter, UI, DB persistence) but the actual ADREC/DARI provider call is a clearly-marked mock, not a real one. See "Step 9 — Live Pricing (stubbed)" below. The rest of this note is the original design-only outline that preceded it and is still accurate about what remains unconfirmed.

## Honesty check before anything else
I don't have confirmed, current documentation for a public ADREC (Abu Dhabi Real Estate Centre) or DARI developer API — access terms, authentication method, endpoint shapes, and rate limits are all **unconfirmed**. These are the kind of government/institutional property-valuation indices that often require a direct partnership or registered-developer agreement rather than a self-serve public API. Before writing any real integration code, someone needs to confirm directly with the provider: (1) that a programmatic API exists at all, (2) its auth model, (3) its terms of use for a commercial wealth-tracking product. Nothing below should be read as "this endpoint exists" — it's the shape the integration would take *once* those facts are confirmed, designed to slot into what's already built.

## Where this already has a landing spot in the app
- `asset_history.source` (migration `0006`) already accepts `'manual' | 'dari' | 'dubailand'` — added specifically so a future automated valuation could be tagged apart from a manual entry, without a schema change.
- The Refresh Valuation dialog (`asset-detail-view.tsx`) already has a Source dropdown with DARI/Dubai Land Department options, currently just tagging the string on a manually-entered number — see the existing "No live DARI or Dubai Land Department integration is configured yet" copy in that dialog.
- `updateAssetValuation()` (`src/app/dashboard/actions.ts`) is the single write path for a new valuation + `asset_history` row, for both manual and (eventually) automated updates.

## Proposed architecture
1. **Adapter module** — `src/lib/market-data/dari.ts` exporting one function: `fetchDariValuation(propertyRef: string): Promise<{ value: number; asOf: string; raw: unknown }>`. Internal HTTP/auth details stay inside this one file so the provider can be swapped or the API version bumped without touching call sites.
2. **Normalized interface, not a DARI-specific one** — define a `MarketDataProvider` type (`{ fetchValuation(propertyRef: string): Promise<...> }`) so `dari.ts` is one implementation of it. If Dubai Land Department's own feed also becomes available later (the UI already has a slot for `'dubailand'` too), it becomes a second adapter behind the same interface, not a special case.
3. **Trigger point** — most likely a manual "Refresh from DARI" action next to the existing "Refresh Valuation" dialog (calls the adapter, then reuses the *existing* `updateAssetValuation(assetId, value, 'dari')` path — no new write logic needed), rather than a background cron job, at least initially: automated recurring valuation pulls raise their own questions (cost per call, provider rate limits, whether a stale property reference silently returns wrong data) that are easier to reason about with a human triggering each refresh.
4. **Credentials** — if the provider requires an API key, it's a server-only secret (never `NEXT_PUBLIC_*`), read only inside the adapter module, following the same pattern as `SUPABASE_SERVICE_ROLE_KEY` in [[Authentication-Security|Authentication & Security]] — never exposed to the client bundle.
5. **Property reference** — DARI/ADREC valuations are keyed by a specific property identifier (parcel/plot number or title deed number), which isn't currently a field on `RealEstateMetadata`. That would need adding (a `dari_property_ref` or similar field in `src/lib/real-estate.ts`, following its existing pattern) before any real call could be made — not done here since this task is design-only.
6. **Failure handling** — the adapter should fail loudly with a specific error (property not found vs. auth failure vs. network error) rather than silently falling back to the manual figure, so a bad automated pull never quietly overwrites a correct manually-entered valuation.

## Mock DLD/ADREC Data Is Read-Only (2026-09-30)

- **Rule**: any DLD or ADREC result with `isMock: true` (sandbox mode — no credentials configured) is returned to the UI for display and certificate preview but **never written to the database**. `refreshDldValuation` and `refreshAdrecValuation` now skip `updateAssetValuation` (which overwrites `assets.current_value`, `metadata.market_valuation` and inserts an `asset_history` row) and the off-plan project-status `assets.metadata` update whenever the provider result is mock. The display-only `getAdrecLiveValuation`, the `adrec-pricing` Edge Function and `getDldCertificate` never wrote anyway.
- **Why**: a sample-mode DLD refresh on 2026-09-30 replaced Ellington House 1 - 713's valuation (3,300,000) with a fabricated 2,728,506, dropping Equity to ~75k and making Net Profit hugely negative.
- **Note on naming**: the table is `asset_history` (there is no `valuation_log` table — "Valuation Log" is just the UI label for its rows).
- **Existing bad data — cleanup Complete (2026-09-30)**: Steve ran the SQL below manually in the Supabase SQL Editor (the automated delete had been blocked by the session's permission check). The `dubailand` row `30830335-aa64-47e0-824b-ff32e62fc7cd` (2,728,506) is deleted and Ellington House 1 - 713 is restored to `market_valuation` 3,300,000 / `current_value` 580,000 — re-verified read-only against the live DB (0 `dubailand` rows remain for that asset). The statement is kept here for the record; it deleted the row and restored the asset's headline values from its latest remaining history point:

```sql
with d as (
  delete from asset_history where source = 'dubailand' and value = 2728506 returning id, asset_id
), latest as (
  select distinct on (h.asset_id) h.asset_id, h.value, h.net_equity
  from asset_history h
  where h.asset_id in (select asset_id from d) and h.id not in (select id from d)
  order by h.asset_id, h.recorded_date desc
)
update assets a
set current_value = l.net_equity,
    metadata = jsonb_set(a.metadata, '{market_valuation}', to_jsonb(l.value))
from latest l
where a.id = l.asset_id
returning a.id, a.name, a.current_value, a.metadata->>'market_valuation';
```

## UAE Open Finance (Al Tareq) Bank Sync — Foundation (2026-10-01)

**Status: the architecture, storage and UI are built; the live bank connection is NOT.** Same posture as the DLD/ADREC clients.

- **Reality check**: Al Tareq is the UAE Open Finance trust framework (Central Bank). Live access is for onboarded third-party providers: a registered client, mTLS certificates and the official API specification. None of that exists for Opes Wealth, and the endpoint shapes in the code follow the generic account-information pattern (OAuth2 authorization-code + PKCE → accounts → balances), **not a verified Al Tareq spec**.
- **Service layer** `lib/banking/altareq.ts` (server-only): PKCE S256 + `state` generation, authorization-URL builder, token exchange/refresh, `listInstitutions`/`fetchAccounts`/`fetchBalances`, typed result unions and error codes. Every real request goes through one stub, `callAltareq()`, which returns **`under_development`** (it needs an mTLS `undici` dispatcher and the real paths). `getBankSyncMode()` → `live` (credentials set), `mock`, or `unconfigured`.
- **Sandbox mode** (`ALTAREQ_SANDBOX_MODE=true`, development only): five fake UAE banks, two accounts each, deterministic balances that are stable within a day and differ across days. **Sandbox data is never written to assets or history** (the lesson of the 2026-09 incident where a mock DLD valuation overwrote a real property): a sandbox connection can only be linked to an EXISTING Cash account, and its balance is only stored on the link row and displayed. Without credentials and without the flag the Connect bank button is disabled — mock is **not** the silent default in production.
- **Token security** (`lib/banking/token-crypto.ts`): access/refresh tokens and the PKCE verifier are encrypted with **AES-256-GCM** (fresh random IV per value, `v1:iv:tag:ciphertext`) using `BANK_TOKEN_ENCRYPTION_KEY` (32 random bytes, base64, server env only, no default). Verified: round trip OK, different ciphertext each time, tampering and a wrong key are both detected. In the database the token columns are additionally unreadable by the browser role (column privileges, migration `0020`), so tokens are only ever read server-side with the service-role client (`utils/supabase/service.ts`), after the user is authenticated and every query is scoped to their id.
- **Flows** (`dashboard/banking/actions.ts`, all require a signed-in, MFA-satisfied session): `startBankConnection` (live: pending row with `state` + encrypted verifier, returns the bank's consent URL; sample: instant), `linkBankAccounts` (link each bank account to a Cash asset; "create new Cash account" is live-only), `syncBankConnection` (live: refresh the token if near expiry, fetch balances, write each balance to its Cash asset + today's `asset_history` row with source `open_finance`, **refusing on a currency mismatch**; failures record `last_sync_error` and mark expired consents), `disconnectBank` (deletes the connection and links; Cash assets and history are kept; **the consent is not yet revoked at the bank** — revoke it in the bank's app too). `dashboard/banking/callback/route.ts` is the redirect target: it validates `state` against the pending connection of the signed-in user (10-minute window), exchanges the code with the stored verifier and stores the tokens encrypted — today it ends on the error redirect because the exchange is the stub.
- **UI** (`cash-bank-card.tsx`, `bank-connect-dialog.tsx`): per account a status badge — Manual / CSV, Synced, Sandbox, Sync error, Consent expired — plus "<bank> · Last synced dd/mm/yyyy hh:mm" (or "Not synced yet"), the last error text, **Sync now** and **Disconnect**; the card header gets **Connect bank** (pick a bank → consent redirect, or sample accounts → map each to a Cash account → first sync). CSV import is unchanged and remains available on every account.
- **Verified**: `tsc`/`eslint`/`build` clean; crypto and the sample/PKCE/URL logic via a disposable script (PKCE S256 challenge matches, live URL carries `code_challenge_method=S256`, unconfigured → `provider_not_configured`, live fetch → `under_development`); the dashboard loads with the new query when migration 0020 is not applied (nothing breaks); the Connect bank button is disabled when unconfigured; all five badge states rendered from sample props. **Not verified**: anything against the database tables (migration `0020` not applied), the connect/link/sync actions end to end, and of course any real bank.
- **To make it real, in order**: (1) apply `0020`; (2) get onboarded as an Al Tareq/Open Finance provider (or use a licensed aggregator/TPP that exposes it) and obtain the client id, certificates and the official spec; (3) implement `callAltareq` (mTLS dispatcher + real paths/scopes/field mapping) and the code/refresh exchange; (4) set the `ALTAREQ_*` variables, `BANK_TOKEN_ENCRYPTION_KEY` and confirm `SUPABASE_SERVICE_ROLE_KEY` in Vercel; (5) add consent revocation, scheduled background sync and transaction import. Note the service-role key then guards bank tokens: treat it as a high-value secret.

## Bank & Broker Logos (2026-10-01)

One component, `components/institution-logo.tsx` (`InstitutionLogo`, `BankLogoByName`): an avatar whose image is loaded from our own route and which falls back to the institution's **initials** if the image can't load.
- **Source, and why not Clearbit / Simple Icons**: Clearbit's free logo API has been shut down, and Simple Icons doesn't carry these banks. The route `app/api/logo/[kind]/[key]/route.ts` takes a registry **key** (never a URL, so it isn't an open proxy), maps it to the registry domain and fetches that site's icon from Google's favicon service server-side (cached a week, 404 on a miss). So these are the institutions' **site icons (favicons), not guaranteed official logo files** — small (some 48px) and occasionally a generic mark. Swapping in hand-picked official SVGs later only means changing that one route.
- **Verified**: all 21 banks and both brokers return an image through the route (Société Générale needs the `www.` host), an unknown key returns 404, and the Banking page renders the logos in the connect buttons. Not verified: how each icon looks at every size, and dark-mode contrast beyond the neutral background chip.
