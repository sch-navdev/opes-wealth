# Market Data Integration

**Status:** Phase 1 Step 9 (Live Pricing) built and deployed as a **stubbed** pipeline — real, working plumbing end-to-end (Edge Function, adapter, UI, DB persistence) but the actual ADREC/DARI provider call is a clearly-marked mock, not a real one. See "Step 9 — Live Pricing (stubbed)" below. The rest of this note is the original design-only outline that preceded it and is still accurate about what remains unconfirmed.

## Honesty check before anything else
I don't have confirmed, current documentation for a public ADREC (Abu Dhabi Real Estate Centre) or DARI developer API — access terms, authentication method, endpoint shapes, and rate limits are all **unconfirmed**. These are the kind of government/institutional property-valuation indices that often require a direct partnership or registered-developer agreement rather than a self-serve public API. Before writing any real integration code, someone needs to confirm directly with the provider: (1) that a programmatic API exists at all, (2) its auth model, (3) its terms of use for a commercial wealth-tracking product. Nothing below should be read as "this endpoint exists" — it's the shape the integration would take *once* those facts are confirmed, designed to slot into what's already built.

## Where this already has a landing spot in the app
- `asset_history.source` (migration `0006`) already accepts `'manual' | 'dari' | 'dubailand'` — added specifically so a future automated valuation could be tagged apart from a manual entry, without a schema change.
- The Refresh Valuation dialog (`asset-detail-view.tsx`) already has a Source dropdown with DARI/Dubai Land Department options, currently just tagging the string on a manually-entered number — see the existing "No live DARI or Dubai Land Department integration is configured yet" copy in that dialog.
- `updateAssetValuation()` (`src/app/dashboard/actions.ts`) is the single write path for a new valuation + `asset_history` row, for both manual and (eventually) automated updates.

## Proposed architecture
1. **Adapter module** — `src/lib/market-data/dari.ts` exporting one function: `fetchDariValuation(propertyRef: string): Promise<{ value: number; asOf: string; raw: unknown }>`. Internal HTTP/auth details stay inside this one file so the provider can be swapped or the API version bumped without touching call sites.
2. **Normalized interface, not a DARI-specific one** — define a `MarketDataProvider` type (`{ fetchValuation(propertyRef: string): Promise<...> }`) so `dari.ts` is one implementation of it. If Dubai Land Department's own feed also becomes available later (the UI already has a slot for `'dubailand'` too), it becomes a second adapter behind the same interface, not a special case.
3. **Trigger point** — most likely a manual "Refresh from DARI" action next to the existing "Refresh Valuation" dialog (calls the adapter, then reuses the *existing* `updateAssetValuation(assetId, value, 'dari')` path — no new write logic needed), rather than a background cron job, at least initially: automated recurring valuation pulls raise their own questions (cost per call, provider rate limits, whether a stale property reference silently returns wrong data) that are easier to reason about with a human triggering each refresh.
4. **Credentials** — if the provider requires an API key, it's a server-only secret (never `NEXT_PUBLIC_*`), read only inside the adapter module, following the same pattern as `SUPABASE_SERVICE_ROLE_KEY` in [[Authentication-Security|Authentication & Security]] — never exposed to the client bundle.
5. **Property reference** — DARI/ADREC valuations are keyed by a specific property identifier (parcel/plot number or title deed number), which isn't currently a field on `RealEstateMetadata`. That would need adding (a `dari_property_ref` or similar field in `src/lib/real-estate.ts`, following its existing pattern) before any real call could be made — not done here since this task is design-only.
6. **Failure handling** — the adapter should fail loudly with a specific error (property not found vs. auth failure vs. network error) rather than silently falling back to the manual figure, so a bad automated pull never quietly overwrites a correct manually-entered valuation.

## Step 9 — Live Pricing (stubbed, built 2026-09-28)

Built ahead of confirmed ADREC/DARI API access, on explicit request, following the "Build with a stubbed adapter" option: the full real pipeline exists and is deployed, but the one piece that can't be real yet — the actual call to ADREC/DARI — is a clearly-marked mock. Nothing here should be mistaken for a working ADREC/DARI integration; see the Honesty check above, which is still accurate.

- **`supabase/functions/refresh-dari-valuation/index.ts`** (new, deployed to the live project as function id `20e72a88-e03d-4090-9278-fb033472ade3`, `verify_jwt: true`) — a Deno Edge Function, not the `dari.ts` server-module shape originally proposed above (a browser-invoked Edge Function fits this app's existing client/server-action split better than a Node-side adapter module would). Accepts `{ assetId, address?, propertyType?, surfaceArea? }` (derived from `RealEstateMetadata` — no new `dari_property_ref` field added yet, per point 5 below, still open). `fetchFromProvider()` is the one clearly-commented stub: returns a deterministic placeholder (`surfaceArea * 12000`, or a flat 500,000 fallback) tagged `isMock: true`, instead of a real HTTP call. Everything around it is real: request validation (400 on missing `assetId`, 405 on non-POST), an `AbortController` timeout (8s placeholder, not a provider-documented figure), and a normalized `{ error: { code, message } }` envelope for `timeout`/`rate_limited`/`invalid_response`/`network_error` — the stub only ever exercises the `timeout` path structurally; a real integration would need to map the provider's actual 429/4xx/5xx shapes onto the same codes. Verified live via direct `curl` against the deployed function: 200 with the expected `{value, asOf, isMock, source}` shape, 400 for a missing `assetId`, 405 for `GET`, and 401 with no `Authorization` header (Supabase's own `verify_jwt` gate, not app code).
- **`src/lib/market-data/dari.ts`** (new, client-side) — `fetchDariValuation(request)`, wraps `supabase.functions.invoke("refresh-dari-valuation", { body: request })`, normalizes both a network-level `error` and an in-body `{error}` payload into one `DariValuationResult` union. This is the `MarketDataProvider`-shaped piece from the original proposal, just invoked from the browser rather than a server module.
- **UI — `src/components/asset-detail-view.tsx`** — a "Refresh from DARI" icon button (`CloudDownload`, distinct from the existing "Refresh Valuation" `RefreshCw` icon so the two aren't confused) next to the existing manual Refresh Valuation trigger, Real Estate assets only. Deliberately **not** a single-click action: since this can immediately overwrite the asset's real current value with placeholder data, it's gated behind an `AlertDialog` confirmation that states outright it uses placeholder/mock data (same honesty-first framing as this note), matching the app's existing double-confirmation pattern for other consequential actions (`DeleteAssetButton`). On confirm: calls `fetchDariValuation()`, then on success reuses the *existing* `updateAssetValuation(assetId, value, "dari")` path exactly as this note originally proposed — no new write logic. Loading state pulses the icon; success/error surfaces as inline text under the header card (`csv_cancel`/`dari_fetching`/`dari_last_updated` etc. — new i18n keys, see [[Localization|Localization]]).
- Verified end-to-end in-browser: confirmation dialog renders correctly (French, the session's active locale), the deployed Edge Function is reached for real (no stubbing needed on the client side once deployed) and returns a mock valuation, `updateAssetValuation` is called with it — the write itself correctly stops at "You must be signed in to update a valuation.", the same dev-environment mock-auth limitation already documented against the CSV upload and Vehicles/Private Equity forms (see [[Authentication-Security|Authentication & Security]]), not a defect in this feature.
- `tsc --noEmit`/`eslint` clean (added `supabase/functions/**` to both the root `tsconfig.json` exclude and `eslint.config.mjs` ignores — Deno code, not part of the Next.js/Node project).
- Ran `get_advisors` (security) against the project after deploying — three pre-existing findings (`handle_new_user`/`rls_auto_enable` SECURITY DEFINER exposure, leaked-password protection disabled), none introduced by or related to this function; left alone as out of scope for this task.
