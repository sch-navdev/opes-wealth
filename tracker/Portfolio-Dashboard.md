## Historical Purchase & Valuation Dates (2026-09-28)
- **Why**: every asset's history curve was anchored to "when the DB row was created," not when the user actually bought or valued it — `syncAssetHistory`'s own doc comment already admitted "there's no separate purchase-date field." For every category except Real Estate (which derives points from its own off-plan payment schedule), the very first `asset_history` point was always stamped today, so a car bought 3 years ago showed a flat curve only starting now.
- **Purchase Date on creation**: `add-asset-dialog.tsx` gained a shared, mandatory `purchase_date` field (native `<Input type="date" required max={today}>`), positioned right after Category, shared across all 5 categories rather than per-category. `assets` gained a real `purchase_date date not null default current_date` column (migration `0012`, see [[Database-Schema|Database Schema]]) rather than stuffing it into jsonb metadata — mirrors how `ticker_symbol`/`created_at` are already top-level columns, and lets the Edit form pre-fill it directly from the row.
- `syncAssetHistory` (`dashboard/actions.ts`) gained a 6th optional `explicitDate` parameter. `addAsset` passes the user's Purchase Date, so a freshly created asset's curve starts there. `updateAsset` does **not** pass it — editing an asset keeps re-stamping today's snapshot exactly as before; backdating only happens at creation, since editing isn't the same action as recording a new historical valuation (that's the next point).
- **Valuation Date on the manual Refresh Valuation dialog** (`asset-detail-view.tsx`): added a `valuationDate` field (defaults to today, `max={today}`), scoped specifically to the one dialog that's genuinely manual entry regardless of its "Source" select (its own existing copy already says so: "No live DARI or Dubai Land Department integration is configured yet — this just tags the source on a manually entered value"). The **Refresh from DARI** button and **Refresh Market Price** flow were deliberately left untouched — both represent a live/fetched-now price, backdating those wouldn't be meaningful.
- `updateAssetValuation` gained an optional 4th `date` parameter, with two deliberate behavior changes beyond just accepting the date:
  1. The `asset_history` write switched from `.insert()` to `.upsert(..., { onConflict: "asset_id,recorded_date" })` (matching `refreshMarketPrice`'s existing pattern) — now that the date is user-chosen rather than always "today," picking a date that collides with an existing row (a prior manual entry, or a Real Estate milestone date) would otherwise throw a unique-constraint error instead of just overwriting that point.
  2. The `assets.update({ current_value, metadata })` call **only runs when the chosen date is today**. Backdating a valuation adds a historical data point; it doesn't redefine what the asset is worth right now — always overwriting `current_value` with a possibly-years-old number would have regressed the portfolio's live totals every time someone back-filled history.
- **Localization**: new keys `purchase_date` and `valuation_date` (EN/FR), used via `t()` for the two new field labels — see [[Localization|Localization]].
- **Verified live**: created a new Vehicles asset with Purchase Date backdated to 2020-05-15 — the form correctly builds and submits the payload (confirmed via the network request body reaching `addAsset` with `purchase_date` included). Submitted a backdated Valuation Date (2023-01-10) through the Refresh Valuation dialog on a Real Estate asset — same confirmation via `updateAssetValuation`'s request payload. Both flows correctly reached the real server action and failed only on this dev environment's known mock-auth limitation ("You must be signed in…"), the same documented constraint as every other write path in this project — not a defect in either new flow. `tsc --noEmit`/`eslint .`/`npm run build` all clean, migration `0012` applied live and `src/types/supabase.ts` regenerated to match.

## Private Equity: Commitment, Called Capital & Capital-Call Liabilities (2026-10-01, roadmap Step 4)

- **Capital-call schedule**: a generator takes % of commitment per call (e.g. 10), first date and frequency (quarterly / semi-annual / annual) and builds the calls — semi-annual from 31 March gives 31 Mar / 30 Sep / 31 Mar … (end-of-month anchored) until the whole commitment is called, the last call trimmed to the remainder. Verified: 500,000 @ 10% from 2025-03-31 → ten 50,000 calls to 2029-09-30; with today = 2026-10-01 four are Paid, six Pending (called 200,000, unfunded 300,000). Calls dated on/before today are generated as **Paid** (assumed honoured) and every row (date, amount, status) is editable/deletable — the UI says so.
- **Liability, like off-plan**: `assetLiability` (`lib/liabilities.ts`) now returns the sum of **pending** capital calls for Private Equity (the analogue of an off-plan property's outstanding instalments, see [[Real-Estate-Multi-Currency|Real Estate & Multi-Currency]]); `grossAssetValue` stays the NAV. So Total Assets = NAV, Total Liabilities includes the pending calls, Net Worth = NAV − pending calls, and the Total Liabilities breakdown lists the fund. The portfolio table and folder subtotal show "Total | Owed" net of pending calls (same code path as mortgaged property). History rows for a fund store `net_equity = NAV − pending calls` (`syncAssetHistory`, `updateAssetValuation`) so the Net Worth chart agrees.
- **Detail page**: a Commitment & capital calls card with commitment / called / unfunded / distributions / liability-counted, a called-% progress bar and the call table (due date, amount, %, Paid / Pending / Overdue).
- **Caveat (flagged in the UI)**: NAV reflects only capital already paid in, so netting FUTURE calls against it understates wealth (the off-plan case differs because the unit's market value already includes the full price). A per-fund switch, "Count pending capital calls as a liability" (default on, as requested), turns the netting off.

## Private Equity: Projected Distributions, Manual Override & Returns (2026-10-01, Step 4 follow-up)

- **Audit of the Step 4 module** — what was missing: it modelled only the call side (calls + liability). It had no projected distributions, no expected multiple / IRR, and no way to switch off the generator and define the timelines by hand.
- **Distributions (years 4–10)** (`lib/private-equity.ts`): `projected_distributions` rows, generated by `generateProjectedDistributions` — total = commitment × expected multiple (default 1.8x), paid once a year from year N to year M (default 4–10, year 1 beginning on the first call so year 4 is three years later), "even" or "back-loaded" (year n weighted n); the last row absorbs cent rounding so the total is exact. Calls keep the 1–5-year phasing with one-click presets (20% a year, or 10% every six months).
- **One-click lifecycle**: "Generate calls & distributions" fills both tables (and the multiple); "Generate calls" alone is kept. Checked: 500,000 commitment, 20% annual calls from 2025-03-31 → 5 calls to 2029-03-31 and 7 distributions 2028-03-31 → 2034-03-31 totalling 900,000 (1.80x), XIRR 12.6%. An early version put year 4 at the 4th anniversary (first distribution 2029, IRR 10.4%); it was corrected so year N begins N-1 years after the first call. The 10% semi-annual preset was not re-measured after that fix.
- **Manual override**: a Lifecycle model ⇄ Manual override switch (`projection_mode`). Manual hides the generators (nothing is generated or overwritten) and exposes "Add call" / "Add distribution" plus typed **expected multiple (x)** and **expected net IRR (%)**; both tables are editable in either mode (date, amount, paid/pending, delete). `fundReturns` returns the computed multiple (distributions ÷ calls) and XIRR (`lib/irr.ts`) from the schedule, or the typed manual figures when set in Manual mode — the form and the detail card say which one is shown.
- **Detail page**: a "Projected cash flows" card — projected distributions, expected multiple, expected IRR, source (model/manual), a J-curve chart (`pe-cash-flow-chart.tsx`: calls below zero, distributions above, cumulative net cash line) and the distribution table.
- **Net Worth unaffected by distributions**: projected distributions are expectations only (stated in the UI). Only pending capital calls count (as before, switchable). The dashboard's forward-looking projection chart still uses its generic growth assumption for a fund; wiring the fund's own cash-flow schedule into that chart is not done.
- **Verified**: tsc/eslint/build clean; the generator/IRR numbers above via a disposable script; in the browser on the live Navtec fund's edit dialog the lifecycle generation produced 5 calls + 7 distributions and the summary "Expected multiple 1.80x · IRR 12.6% (computed from the schedule)", the Manual tab hid the generator and showed the manual fields ("2.50x · IRR 15.0% (manual targets override computed)"), and the chart rendered 12 bars + the cumulative line from sample data. Nothing was saved to the live DB, so persistence of the new fields (plain `assets.metadata` JSON, no migration) is verified by code only.

## Asset photos moved to Supabase Storage (2026-10-02)

- **Before:** each photo was a base64 string inside `assets.images`, and the dashboard fetched all of them (up to 3 per asset) on every load. **Now:** photos are real files in the public bucket `asset-photos` and `assets.images` holds only their public URLs.
- **Bucket (migration `0027_asset_photos_bucket.sql`):** public read, 3 MB limit, `image/webp` + `image/jpeg` only. Storage policies let an authenticated user insert/update/delete **only inside their own folder** (`<auth.uid()>/…`); there is no select policy, so the bucket cannot be listed. **Public means anyone holding a URL can open the photo** (URLs contain random UUIDs and are only shown to the asset's owners, but they are not access-controlled).
- **Upload (browser):** `lib/asset-photos-client.ts` re-encodes the picked file to **WEBP at ≤1440px, quality 0.9** (JPEG with a white background where the browser can't encode WEBP), never cropping or upscaling, uploads it as `<user id>/<uuid>.webp` with a 1-year cache header and returns the public URL. Photos uploaded in an editing session that is then dismissed, or removed again before saving, are deleted straight away.
- **Server (`dashboard/actions.ts`):** `parseImages` now accepts only URLs inside our bucket (`lib/asset-photos.ts#isAllowedPhotoSrc`) or a size-capped legacy `data:image/…` string — an arbitrary external URL would otherwise be loaded by every co-owner's browser. `updateAsset`, `deleteAsset` and `batchDeleteAssets` delete the files of photos that are dropped or whose asset is deleted (`lib/asset-photos-server.ts`, best effort, service role). A pending co-owner edit does not clean up until applied. `next.config.ts` allows the Supabase host for `<Image>`.
- **Existing photos:** `scripts/migrate-asset-images.mts` converts remaining base64 photos (original bytes, no re-encoding) into bucket files and rewrites the rows; dry run by default, `--yes` to write, idempotent, a row is updated only after all its photos uploaded. Dry run against production found **5 photos on 5 assets (≈0.1 MB)**. Not yet run for real: it needs migration 0027 applied first. Until then old base64 photos keep displaying (both forms render as `<img src>`).
- **Thumbnails (added before 0027 was applied):** Supabase's on-the-fly image transformation is a paid-plan feature (the project is on Free), so the thumbnail is made **at upload time** instead — each photo is stored as two files in the owner's folder, `<uuid>.webp` (≤1440px, q0.9) and `<uuid>-thumb.webp` (≤192px, q0.8, typically a few KB — an estimate, not measured). Only the full URL is saved in `assets.images`; `photoThumbUrl` derives the thumbnail URL from it (`lib/asset-photos.ts`), and lists, avatars and the dialog previews use it (`loading="lazy"`), while the photo viewer loads the full file. Both files are deleted together; an upload whose thumbnail fails removes the full file. Legacy base64 photos are used as-is. `scripts/migrate-asset-images.mts` now also creates thumbnails with `sharp` (and converts PNG to WEBP, because the bucket only accepts WEBP/JPEG). No SQL change was needed for this: the existing own-folder policies cover both files. **Not done:** the profile avatar (`profiles.avatar_base64`) is unchanged; orphaned files are possible if a browser closes mid-session.
- **Verified:** `tsc`, `eslint`, `next build`, a script check of the URL helpers (own-bucket URLs accepted; external hosts, other buckets, `..`, query strings, oversized/odd schemes rejected) and the migration dry run. **The upload itself has not been exercised** (bucket doesn't exist until 0027 is applied).

## Vehicles: Blue Book valuation and depreciation (2026-10-02)

- **Blue Book / Argus valuation** (`components/vehicle-bluebook-dialog.tsx`, card on the vehicle page): the official price-guide value, kept SEPARATE from the market value. The label follows the language: Blue Book (en), Cote Argus (fr), Eurotax (es, it), Schwacke (de), plus generic price-guide wording in ar/ru/hi/zh. Stored in `metadata.blue_book_value / _source / _date / _document`. **Not fetched live:** Argus, Kelley, Parkers and the others are closed or paid B2B services and there is no API access (the existing market-value provider is still disabled, see [[Real-Estate-Multi-Currency|Real Estate & Multi-Currency]]), so the value comes from the user: **upload the guide's PDF** (`readBlueBookDocument`, `lib/bluebook-parser.ts`, via `pdf-parse` like the tenancy contract) or type it, or start from the depreciation estimate (clearly labelled as an estimate). The reader is heuristic: it proposes a value, date, guide name and the other amounts it saw, and the user confirms before `saveBlueBookValuation` stores anything; a scanned PDF has no text layer and is reported as unreadable. The PDF itself is not stored, only its file name. Optional "also use as the current value" updates `current_value` and the history. Tested on English, French and UK sample text; **not tested on real guide PDFs** (formats vary).
- **Depreciation** (`lib/vehicle-depreciation.ts`, fields in `vehicle-fields.tsx`): signed yearly change in percent (negative = depreciation, **positive = appreciation allowed**), a first-year rate and a later-year rate, editable by hand ("Use suggested rates" resets). A **second-hand** tick skips the showroom drop (the first year uses the yearly rate) and eases the rate by 25% for cars already 5+ years old at purchase. Suggested rates by type, from published UAE and US guides (Oct 2026): Japanese -17.5% / -9%, luxury SUV (Patrol, Land Cruiser) -12.5% / -6.5%, European luxury -30% / -17.5%, EV -35% / -17.5%, general -25% / -12.5%; the "sports / exotic" group (-15% / -7%) is **our assumption**, not from the sources. The form shows the estimated value today (purchase price compounded from the purchase date); the detail page shows it next to the Blue Book value. It does not change net worth by itself.
- **Fixes after a real Argus certificate (2026-10-02):** the parser reads the supplied French Argus attestation correctly (81 240 EUR, 29/09/2026, source Argus), so the failure the user saw was elsewhere; the read action now logs and shows the underlying server error. The guide value now has its **own currency** (any of the app's currencies; the PDF's currency is detected) and is a **dated log** (`metadata.blue_book_log`, each entry removable; the earlier single value migrates into it on read). The vehicle chart shows **three curves**: market value (recorded valuations only), purchase price (flat from the purchase date) and Blue Book (converted to the asset currency at today's rates). The old chart overwrote a market value dated on the purchase date with the purchase price; that no longer happens.
