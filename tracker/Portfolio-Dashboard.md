# Portfolio Dashboard

**Status:** Done (foundation) — Phase 1, Step 7. Extended with edit/delete and multi-currency display.

## Foundation
- `src/app/dashboard/actions.ts` — server action `addAsset(formData)`: reads `name`, `category_id`, `quantity`, `current_value`, `currency` (default `'USD'`) from the form, resolves the current user via `getUser()`, inserts into `assets` with `profile_id` set to that user's id, and calls `revalidatePath('/dashboard')` on success.
- `src/components/add-asset-dialog.tsx` — Client Component using shadcn `Dialog`/`Select`/`Input`/`Label`. Submits `addAsset` via a client-driven `startTransition` (not a bare form `action`) so it can show inline errors and close the dialog only on success. Category dropdown is populated from the `asset_categories` passed in as a prop.
- `src/app/dashboard/page.tsx` — now also queries `asset_categories` (all rows, for the dropdown) and the signed-in user's own `assets` (joined with `asset_categories(name)`), in parallel. Renders `AddAssetDialog` at the top of the page and a shadcn `Table` of the user's assets below it (Name / Category / Quantity / Value, liabilities shown in destructive red with a leading `-`). Empty state shown when there are no assets yet.
- Installed shadcn `dialog`, `select`, `table` components (`src/components/ui/`); fixed the same CLI `cn`-package import issue as previous component installs.
- **Resolved**: the missing-`profiles`-row gap that would have made `addAsset` fail with a foreign-key violation is now fixed by `supabase/migrations/0002_user_profile_trigger.sql` (see [[Database-Schema|Database Schema]]).
- Not yet verified against a live Supabase instance (dev server was only exercised while signed out, since these routes are visible only to newly-verified sessions and no test account/schema deployment was available in this session).

## Edit/Delete Asset Actions
`src/app/dashboard/actions.ts` gained `updateAsset(id, formData)` (same field extraction as `addAsset`, `.update(...).eq('id', id).eq('profile_id', user.id)`, `revalidatePath('/dashboard', 'layout')`) and `deleteAsset(id)` (same ownership-scoped `.delete()`). Both re-check `profile_id = user.id` explicitly in addition to relying on RLS, so a row that isn't the caller's own is a no-op rather than a surprise. `add-asset-dialog.tsx` now accepts an optional `asset` prop; when present it's in edit mode — every field is pre-filled from that asset (including [[Real-Estate-Multi-Currency|Real Estate]] metadata), the trigger becomes an `Edit`-icon-only button instead of "Add Asset", the title/description/submit-button text switch to "Edit Asset"/"Save Changes", and submission calls `updateAsset(asset.id, formData)` instead of `addAsset`. Installed shadcn `alert-dialog` (same `cn`-import fix as before); `src/components/delete-asset-button.tsx` wraps it — clicking the `Trash2`-icon button opens a double-confirmation dialog ("Are you sure you want to delete this asset? This action cannot be undone."), and `AlertDialogAction`'s `onClick` calls `e.preventDefault()` before running `deleteAsset` so the dialog stays open while the delete is pending and only closes on success (Radix's `Action` would otherwise close it immediately on click). `dashboard/page.tsx`'s table gained a right-aligned "Actions" column rendering both per row.

Verified visually in the browser (via a disposable local-only preview route, removed before committing): editing a sample Real Estate asset correctly pre-fills every field and the button reads "Save Changes"; the delete button opens the exact confirmation copy requested.

## Historical Purchase & Valuation Dates (2026-09-28)
- **Why**: every asset's history curve was anchored to "when the DB row was created," not when the user actually bought or valued it — `syncAssetHistory`'s own doc comment already admitted "there's no separate purchase-date field." For every category except Real Estate (which derives points from its own off-plan payment schedule), the very first `asset_history` point was always stamped today, so a car bought 3 years ago showed a flat curve only starting now.
- **Purchase Date on creation**: `add-asset-dialog.tsx` gained a shared, mandatory `purchase_date` field (native `<Input type="date" required max={today}>`), positioned right after Category, shared across all 5 categories rather than per-category. `assets` gained a real `purchase_date date not null default current_date` column (migration `0012`, see [[Database-Schema|Database Schema]]) rather than stuffing it into jsonb metadata — mirrors how `ticker_symbol`/`created_at` are already top-level columns, and lets the Edit form pre-fill it directly from the row.
- `syncAssetHistory` (`dashboard/actions.ts`) gained a 6th optional `explicitDate` parameter. `addAsset` passes the user's Purchase Date, so a freshly created asset's curve starts there. `updateAsset` does **not** pass it — editing an asset keeps re-stamping today's snapshot exactly as before; backdating only happens at creation, since editing isn't the same action as recording a new historical valuation (that's the next point).
- **Valuation Date on the manual Refresh Valuation dialog** (`asset-detail-view.tsx`): added a `valuationDate` field (defaults to today, `max={today}`), scoped specifically to the one dialog that's genuinely manual entry regardless of its "Source" select (its own existing copy already says so: "No live DARI or Dubai Land Department integration is configured yet — this just tags the source on a manually entered value"). The **Refresh from DARI** button and **Refresh Market Price** flow were deliberately left untouched — both represent a live/fetched-now price, backdating those wouldn't be meaningful.
- `updateAssetValuation` gained an optional 4th `date` parameter, with two deliberate behavior changes beyond just accepting the date:
  1. The `asset_history` write switched from `.insert()` to `.upsert(..., { onConflict: "asset_id,recorded_date" })` (matching `refreshMarketPrice`'s existing pattern) — now that the date is user-chosen rather than always "today," picking a date that collides with an existing row (a prior manual entry, or a Real Estate milestone date) would otherwise throw a unique-constraint error instead of just overwriting that point.
  2. The `assets.update({ current_value, metadata })` call **only runs when the chosen date is today**. Backdating a valuation adds a historical data point; it doesn't redefine what the asset is worth right now — always overwriting `current_value` with a possibly-years-old number would have regressed the portfolio's live totals every time someone back-filled history.
- **Localization**: new keys `purchase_date` and `valuation_date` (EN/FR), used via `t()` for the two new field labels — see [[Localization|Localization]].
- **Verified live**: created a new Vehicles asset with Purchase Date backdated to 2020-05-15 — the form correctly builds and submits the payload (confirmed via the network request body reaching `addAsset` with `purchase_date` included). Submitted a backdated Valuation Date (2023-01-10) through the Refresh Valuation dialog on a Real Estate asset — same confirmation via `updateAssetValuation`'s request payload. Both flows correctly reached the real server action and failed only on this dev environment's known mock-auth limitation ("You must be signed in…"), the same documented constraint as every other write path in this project — not a defect in either new flow. `tsc --noEmit`/`eslint .`/`npm run build` all clean, migration `0012` applied live and `src/types/supabase.ts` regenerated to match.
